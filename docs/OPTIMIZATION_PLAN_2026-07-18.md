# MxTools 优化计划（2026-07-18）

## 目标

在不破坏现有工具功能的前提下，优先解决 OCR 误识别、界面拥挤和质量门禁失效问题，并为后续持续优化建立可量化的基线。

## 当前基线与主要问题

- 前端生产构建、Rust `cargo check` 和现有 18 个前端测试通过。
- ESLint 配置使用 TypeScript 文件，但项目未安装 ESLint 9 所需的 `jiti`，`npm run lint` 无法执行。
- Rust 严格 Clippy 有 16 个项目内告警；OCR 模块存在复杂五元组返回值、重复分支等可维护性问题。
- RapidOCR 已作为外置 ONNX 模型接入，但当前仍使用 PP-OCRv3 检测 + PP-OCRv4 英文识别模型。
- RapidOCR 将很小的 HUD ROI 原样送入检测模型，缺少放大、多预处理候选和置信度筛选。
- OCR 标点归一化顺序错误：Unicode 冒号、负号等在归一化前就被白名单删除。
- 无标签解析过于宽松，可能把 ROI 中任意数字当作角度，或把最大数字当作距离。
- 前端选择 RapidOCR 时实际不会启用 Windows OCR 兜底，与界面提示不一致。
- OCR 包只检查文件是否存在，不检查 manifest 版本；升级模型后旧包仍可能被误判为可用。
- 全局 `.v-card-text { padding: 0 }` 清除了所有 Vuetify 卡片正文留白，是大量页面显得拥挤的直接原因。
- 自定义标题栏使用可点击 `div`，缺少键盘操作、可访问名称和清晰的焦点状态。
- OCR 设置与诊断信息混在一起，原始 ROI 数值长期裸露，主路径信息层级不清晰。

## 分阶段实施

### P0：本轮落地

1. 修复 ESLint 配置并恢复前端质量门禁。
2. OCR 包升级为 PP-OCRv5 mobile 检测/英文识别模型，继续离线使用 ONNX Runtime。
3. 增加 OCR 包版本校验、自动引擎模式和真正的 RapidOCR → Windows OCR 兜底。
4. 对小 ROI 做等比像素放大、多变体识别和置信度择优；收紧无标签数字解析。
5. 将 OCR 返回值改为命名结构，并在界面展示实际引擎与置信度，便于用户校准。
6. 恢复卡片正文间距、优化 OCR 面板层级、隐藏高级 ROI 数值，并完善标题栏可访问性。
7. 修复项目内严格 Clippy 问题，补充 OCR 解析与模型包版本测试。

### P1：需要真实样本集

1. 收集不同分辨率、亮度、语言和 HUD 缩放下的脱敏截图，建立固定 OCR 回归集。
2. 为角度、距离分别统计命中率、误报率和平均耗时，而不是凭单张截图调参。
3. 根据回归集决定是否增加 PP-OCRv5 server 档位，或训练仅包含 `ang / 数字 / m` 的小型识别模型。
4. 加入连续 2–3 次截图的时序一致性校验，过滤单帧跳变。

### P2：架构与体积

1. 拆分超过 800 行的 Alter Q 设置、校准组件及超大 i18n 文件。
2. 为 Tauri IPC 增加统一错误码与前端错误映射，减少字符串匹配。
3. 分析 Vuetify 与通用依赖大包，按页面按需加载并设置 bundle size budget。
4. 在 CI 中固定执行前端 lint/test/build、Rust fmt/check/clippy/test。

## 验收标准

- `npm run lint`、`npm test`、`npm run build` 全部通过。
- `cargo check`、项目内 `cargo clippy -- -D warnings` 和 OCR Rust 单元测试通过。
- 旧 OCR 包会被识别为需要升级；自动模式至少能使用一个可用引擎。
- Unicode 标点、常见 O/0 与 I/1 混淆有回归测试；包含多个无标签数字时不再冒进误判。
- OCR 结果页能看到实际使用的引擎和置信度，原始 ROI 数值默认收起。
- 卡片正文恢复一致留白，标题栏按钮支持键盘焦点和辅助技术识别。
